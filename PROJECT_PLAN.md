# PlanToSave — Project Plan

## Overview

A multi-user savings and spending planner built with Blazor Web App (.NET 8), PostgreSQL, and hosted on Render. Users can model their finances using a stock/flow paradigm, build monthly spending plans, track actual vs. planned flows, and set savings goals that auto-generate contribution schedules.

---

## Tech Stack

| Concern | Choice |
|---|---|
| Frontend | Blazor Web App (.NET 8), Server render mode |
| Backend | ASP.NET Core 8 (hosted in same process) |
| Database | PostgreSQL (Render managed) |

| Auth | ASP.NET Core Identity + Google OAuth 2.0 (via OIDC) |
| Hosting | Render (Web Service + PostgreSQL) |
| Containerization | Dockerfile (Render native deploy) |

## Domain Model

### Core Concepts

**Stock accounts** hold a running balance. Flows into and out of them change that balance.  
**Flow accounts** (Income, Expense) are pipes only — they have no balance, only period totals.

### Account Types

| Type | Stock? | Notes |
|---|---|---|
| `Income` | No | Represents money entering from the outside world (salary, freelance, etc.) |
| `Expense` | No | Represents money leaving to the outside world (groceries, utilities, etc.) |
| `Checking` | Yes | Day-to-day bank account |
| `Savings` | Yes | General or goal-specific savings account |
| `Credit` | Yes | Credit card — starts at 0, goes negative when spent, paid down by transfers |
| `Investment` | Yes | Retirement, brokerage, etc. |

### Rules for Flows

- Income accounts may only appear as `FromAccount` (money flows *from* income *into* the plan)
- Expense accounts may only appear as `ToAccount` (money flows *out* of the plan *to* expenses)
- Stock accounts may appear on either side of a flow

## Data Model

```
Users                        (managed by ASP.NET Core Identity)
  Id (string, GUID)
  Email
  DisplayName

Accounts
  Id (Guid)
  UserId (FK → Users)
  Name
  Type (enum: Income | Expense | Checking | Savings | Credit | Investment)
  Description
  IsArchived (bool)
  CreatedAt

FlowTemplates                (recurring monthly flow definitions)
  Id (Guid)
  UserId (FK → Users)
  FromAccountId (FK → Accounts)
  ToAccountId (FK → Accounts)
  Amount (decimal, 2dp)
  Description
  IsActive (bool)
  CreatedAt

MonthlyPlans
  Id (Guid)
  UserId (FK → Users)
  Year (int)
  Month (int)
  Status (enum: Draft | Active | Closed)
  CreatedAt
  UNIQUE (UserId, Year, Month)

PlannedFlows
  Id (Guid)
  MonthlyPlanId (FK → MonthlyPlans)
  FromAccountId (FK → Accounts)
  ToAccountId (FK → Accounts)
  Amount (decimal, 2dp)
  Description
  TemplateId (FK → FlowTemplates, nullable)  -- seeded from a template?
  GoalId (FK → Goals, nullable)              -- generated by a goal?

ActualFlows
  Id (Guid)
  UserId (FK → Users)
  FromAccountId (FK → Accounts)
  ToAccountId (FK → Accounts)
  Amount (decimal, 2dp)
  Date (DateOnly)
  Description
  PlannedFlowId (FK → PlannedFlows, nullable) -- linked to a plan item?
  CreatedAt

Goals
  Id (Guid)
  UserId (FK → Users)
  Name
  Description
  TargetAccountId (FK → Accounts — must be Stock type)
  TargetAmount (decimal, 2dp)
  TargetDate (DateOnly)
  StartDate (DateOnly)
  SourceAccountId (FK → Accounts — where contributions come from)
  IsComplete (bool)
  CreatedAt
```

### Balance Computation

Stock account balance = SUM(ActualFlows where ToAccountId = account) − SUM(ActualFlows where FromAccountId = account)

This is computed on the fly from transaction history — fully auditable, no denormalized state to go out of sync. A database view or EF Core query projection handles this efficiently.

## Authentication — Google OAuth

1. Register app in Google Cloud Console → OAuth 2.0 Client ID (Web Application)
2. ASP.NET Core Identity provides the user store (users table in PostgreSQL)
3. `AddAuthentication().AddGoogle(...)` wired up in `Program.cs`
4. On first Google login, Identity creates a local user record linked to the Google subject claim
5. All entities include `UserId` FK — a base service layer always scopes queries to the calling user's ID

Redirect URIs to register in Google Console:
- Local dev: `https://localhost:5001/signin-google`
- Production: `https://<your-render-app>.onrender.com/signin-google`

## Key Design Decisions & Rationale

| Decision | Rationale |
|---|---|
| Blazor Server (not WASM) | No cold-start penalty; real-time balance updates via SignalR; simpler auth flow |
| Compute balances on-the-fly | Fully auditable; eliminates risk of cached balance drift; easy to add DB view later |
| Single ASP.NET Core host | Simplest Render deployment — one service, one Dockerfile |
| Per-entity UserId FK | Simplest multi-tenancy model; no risk of cross-user data leakage |
| FlowTemplate separate from PlannedFlow | Templates are definitions; plan items are instances — avoids mutation of historical plans when templates change |
| Goals generate PlannedFlows | Keeps the planning UI uniform — goal contributions are just planned flows tagged with a GoalId |
